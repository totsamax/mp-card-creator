- **D-05:** First 4 slides are `default: true`, ids `main`/`infographic`/`scale`/`lifestyle`, descriptions pre-filled from `prompts.images.json`. Extra slides are `default: false`, id `custom-{uuid}`, empty description.

- **D-09:** Arbitrary files attach per slide. Saved via `versionStore.putArtifact` to YDB/S3 under `{article}/03-images/slide-files/{slideId}/{filename}`. `slides[]` holds storage refs (not base64).

- **D-11:** `POST /lines/:id/slides/:slideId/generate-prompt` — takes description, returns `generatedPrompt` (inline synchronous LLM call).
- **D-12:** `POST /lines/:id/slides/:slideId/regenerate` — generates one image for the slide; leaves other steps untouched.

## Summary

This is a **brownfield feature phase** that touches all four tiers of an already-working pipeline: the React SPA (`frontend/PipelineApp.jsx`), the plain-Node HTTP router (`functions/api/index.js`), the image-generation step (`functions/step-images/index.js`), and the storage layer (`layers/shared/versionStore.js`). **No new libraries are needed** — CLAUDE.md forbids stack changes, and every capability this phase requires already has an established pattern in the codebase: inline LLM `fetch` calls (from `step-texts`), manifest read-merge-write (`updateManifest`), artifact blob storage (`putArtifact`), multipart file upload (busboy in `local-server.js`), and the `pp-` design system + lucide icons in the frontend.

The core architectural shift is small but load-bearing: **`step-images` must stop reading prompts from `require('config/prompts.images.json')` at module load and instead read the per-article `slides` config from the manifest at handler-invocation time**, falling back to the JSON file only to seed defaults. Everything else is additive: three new API routes, one new frontend editor section, and a slides-defaults builder.

Two genuine design tensions need a decision before/during planning (both flagged in the Assumptions Log): (1) **per-size vs per-article prompts** — the current `infographic` prompt bakes in size-specific dimensions via `{{tokens}}`, but slides are per-article; the phase must decide how per-size physical data (dimensions, toy height) reaches the image when the stored `generatedPrompt` is authored once; and (2) **custom slides have no template file and no fixed `imageType`**, so the image-generation path, artifact naming, and the frontend grid (which today iterates a fixed `IMAGE_TYPES` array) all need to become slide-driven.

**Primary recommendation:** Store `slides` as `manifest.steps['03-images'].slidesConfig` (co-located with the consuming step, written via `updateManifest(article, '03-images', { slidesConfig })`). Reuse `step-texts`'s inline `fetch` LLM pattern for `generate-prompt`. Reuse the `photos` pseudo-step convention (`putArtifact(article, 'slide-files', 1, '{slideId}/{filename}', buf)`) for attachments so retrieval falls through the existing `handleGetArtifact` route. Use **POST (not PUT)** for saving slides because the local server's CORS `Access-Control-Allow-Methods` only permits `GET, POST, OPTIONS`.

### Pattern 1: Inline synchronous LLM call (generate-prompt, D-11)
**What:** A short chat/completions request that turns a Russian description into an English image prompt.
**When to use:** The `POST /slides/:slideId/generate-prompt` handler — reply synchronously with the prompt.
**Example — mirror `step-texts` exactly (OpenRouter-priority, OpenAI fallback):**
```javascript
// Source: functions/step-texts/index.js:113-190 (generateTexts) — reuse verbatim shape
const OPENAI_BASE  = (process.env.OPENAI_BASE_URL || 'https://api.openai.com/v1').replace(/\/$/, '');
const OPENAI_MODEL = process.env.OPENAI_MODEL || 'gpt-4o-mini';   // D-11: gpt-4o-mini is enough

async function generatePrompt(description, sizeRecord) {
  const apiKey = process.env.OPENAI_API_KEY;
  if (!apiKey) {
    // OFFLINE/TEST stub — deterministic, no network (see Common Pitfall 4)
    return `${description} — mold ${sizeRecord?.moldName ?? ''}, ${sizeRecord?.color ?? ''}`;
  }
  const system = 'You write concise image-generation prompts for the gpt-image-2 API for '
    + 'product marketplace slides. Output only the prompt, no explanation. Language: English.';
  const user = `${description}\n\nContext: mold «${sizeRecord.moldName}», color ${sizeRecord.color}, `
    + `size ${sizeRecord.moldSize} cm (${sizeRecord.moldLength}×${sizeRecord.moldWidth}×${sizeRecord.moldHeight} cm).`;
  const res = await fetch(`${OPENAI_BASE}/chat/completions`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${apiKey}` },
    body: JSON.stringify({ model: OPENAI_MODEL, max_tokens: 400,
      messages: [{ role: 'system', content: system }, { role: 'user', content: user }] }),
  });
  if (!res.ok) throw new Error(`generate-prompt LLM ${res.status}: ${await res.text()}`);
  const data = await res.json();
  return data.choices[0].message.content.trim();
}
```
> Note: `step-texts` prefers `OPENROUTER_API_KEY` when present. MEMORY.md records that this project routes all AI calls through `api.apiframe.ai` with a single `OPENAI_API_KEY`. Keep it simple: use the `OPENAI_BASE_URL` + `OPENAI_API_KEY` chat/completions path (the fallback branch of `generateTexts`). `[ASSUMED]` — confirm apiframe exposes an OpenAI-compatible `/chat/completions` for gpt-4o-mini; if not, the same base already serves gpt-4o for the vision critic (`step-images.js:335`), so chat/completions is available.

### Pattern 2: Manifest read-merge-write for slide config
**What:** Persist the whole `slidesConfig` object; `deepMerge` + per-article lock handle concurrency.
**When to use:** Save-slides route and any single-field slide update.
**Example:**
```javascript
// Source: layers/shared/versionStore.js:31-57 (updateManifest) + :282 (deepMerge)
// Whole-config save (POST /slides):
await store.updateManifest(article, '03-images', { slidesConfig: { feedbackSuffix, slides } });
```
**Critical:** `deepMerge` **replaces arrays wholesale** (`versionStore.js:286-287`: `if (Array.isArray(value)) result[key] = value`). So writing `{ slidesConfig: { slides: [...] } }` overwrites the entire slides array — correct for a full save, but for a **single-slide update you must read the current array, modify the one slide, and write the whole array back**. The per-article `withManifestLock` (`versionStore.js:258`) serialises concurrent writers, so a read-modify-write inside one handler is safe against parallel handlers.

### Pattern 3: Multipart file upload → putArtifact (reuse `photos` convention)
**What:** Accept arbitrary reference files per slide, store as blobs, keep only refs in `slides[]`.
**When to use:** The slide-file upload route (D-09).
**Example:**
```javascript
// Source: functions/api/index.js:241-273 (handleCreateLine multipart path) — reuse validation
// local-server.js already populates event.files for multipart requests.
for (const f of event.files) {
  if (!f.mimeType || !f.mimeType.startsWith('image/')) return respond(400, {error:'…'}); // relax if non-images allowed
  const safeName = path.basename(f.filename||'').replace(/[^a-zA-Z0-9._-]/g,'_');
  // pseudo-step 'slide-files', version 1 — mirrors putArtifact(article,'photos',1,…) at api/index.js:271
  await store.putArtifact(article, 'slide-files', 1, `${slideId}/${safeName}`, f.buffer);
}
// ref stored in slide.files[]: retrievable via GET /lines/:id/steps/slide-files/artifacts/<ref>
```
> `putArtifact` name may contain a subpath (`{slideId}/{filename}`): the local adapter does `mkdir(path.dirname(p),{recursive:true})` (`versionStore.js:61`) and S3 keys are slash-native. D-09 wanted `{article}/03-images/slide-files/{slideId}/{filename}`; using pseudo-step `slide-files` yields `{article}/slide-files/v1/{slideId}/{filename}` — functionally equivalent and it slots into the existing `handleGetArtifact` route with **no new retrieval code**.

### Pattern 4: New router branches
**What:** Add route matchers in `exports.handler` (`api/index.js:97-161`) alongside the existing `/manifest`, `/steps/...` matchers.
**Example:**
```javascript
// after the article-extraction block (api/index.js:119)
```

Validate `slideId` (e.g. `/^[a-zA-Z0-9_-]{1,64}$/`, matches `custom-<uuid>`) exactly as `article` is validated (`api/index.js:120`).

### Anti-Patterns to Avoid
- **Writing prompts back to `prompts.images.json`** — explicitly forbidden by D-02. That file is read-only defaults.
- **Adding a second polling loop in the frontend** — UI-SPEC mandates reusing the existing 5s manifest poll (`PipelineApp.jsx:816`) and the optimistic-running pattern.
- **Using PUT for the save route** — blocked by local-server CORS; use POST.
- **Storing file bytes (base64) in `slides[]`** — D-09 says store refs only. Blobs go to `putArtifact`.
- **Keeping `require('config/prompts.images.json')` as the generation source** — must become a manifest read per invocation; the `require` stays only for seeding defaults.
- **Iterating the hardcoded `IMAGE_TYPES` in ImageView to render results** — with custom slides this must become slide-driven, or custom-slide images won't display.

## Common Pitfalls

### Pitfall 1: `deepMerge` silently overwrites the whole slides array
**What goes wrong:** A single-slide save (e.g. persisting one `generatedPrompt`) sent as `{ slidesConfig: { slides: [oneSlide] } }` **wipes the other slides**.
**Why it happens:** `deepMerge` replaces arrays wholesale (`versionStore.js:286-287`), it does not merge by index/id.
**How to avoid:** For any single-slide change, read the current `slidesConfig.slides`, mutate the target slide by `id`, write the **entire** array back. Prefer a whole-config POST from the UI on save.
**Warning signs:** Slides disappearing after editing one of them.

### Pitfall 2: PUT is blocked by CORS
**What goes wrong:** `PUT /lines/:id/slides` fails browser preflight — `Access-Control-Allow-Methods` is `GET, POST, OPTIONS` (`local-server.js:167`).
**Why it happens:** D-10 literally says "PUT", but the server never advertised PUT.
**How to avoid:** Use `POST /lines/:id/slides` for saving, **or** add `PUT` to `corsHeaders()` and the router. Recommend POST (smaller change, no server edit).
**Warning signs:** Save button 405/CORS error in browser console; works in a curl/node test (which skips CORS) but not in the UI.

### Pitfall 3: Per-size dimensions vanish when the prompt is authored once per article
**What goes wrong:** The current `infographic` prompt injects `{{moldLength}}×{{moldWidth}}×{{moldHeight}}` and `{{moldSize}}` per size (`step-images.js:126`). Slides are per-article, so a single stored `generatedPrompt` cannot carry 5 different sizes' dimensions — all 5 infographics would show one size's numbers (or none).
**Why it happens:** The generator-critic loop runs per size (`XS…XL`), but the new config is per line.
**How to avoid (decision needed — see Assumptions A1):** Recommended — `step-images` appends a resolved per-size data block to the stored `generatedPrompt` at generation time (e.g. `\nDimensions: {L}×{W}×{H} cm, size {moldSize} cm.` built from the current `sizeRecord`), so the LLM-authored prose stays size-agnostic and physical facts stay accurate. Alternative: allow `{{tokens}}` to survive in `generatedPrompt` and keep `substitutePrompt` — fragile (depends on the LLM emitting tokens). **Flag for user/planner.**
**Warning signs:** All size infographics render identical dimension callouts.

### Pitfall 4: New code can't be tested offline — no image-generation stub exists
**What goes wrong:** `functions/step-images` `generateImage` **throws `'OPENAI_API_KEY not set'`** without a key (`step-images.js:179`) and the handler returns 500. **Verified now:** `node --test test/step-images.test.js` → **4 of 7 tests FAIL** offline (the ones expecting real generation); only `buildEditRequest` and route-contract tests pass. The test file's comment about a "stub branch gated on `!apiKey`" describes intent that does **not** exist in current code. `[VERIFIED: ran suite 2026-07-03 — pass 3 / fail 4]`
**Why it happens:** No offline fallback for the actual pixel generation.
**How to avoid:** Give the **new `generate-prompt` handler an explicit no-key stub** (return a deterministic string, as in Pattern 1) so its tests run without network. For single-slide `regenerate`, test the **route contract (202) and the manifest/slidesConfig plumbing**, not real image bytes — same boundary the passing existing tests use. Do not assume `03-images` generation is testable end-to-end offline.
**Warning signs:** New tests hang (real network) or 500 in CI.

### Pitfall 5: Custom slides have no template file and no fixed imageType
**What goes wrong:** The OpenAI `images/edits` fallback reads `SHARED/templates/{imageType}.png` (`step-images.js:285`) — a `custom-<uuid>` slide has no such template and throws. Artifact naming `{size}_{imageType}.png` and the frontend grid (`IMAGE_TYPES.map`, `PipelineApp.jsx:317`) assume the fixed 4 types.
**Why it happens:** The pipeline was built for exactly 4 known image types.
**How to avoid:** For custom slides, use the text+photo generation path (apiframe / `images/generations`), skip the template read, name artifacts `{size}_{slideId}.png`, and drive both `handleGetArtifact` version-lookup and `ImagesView` rendering from the slides list rather than the `IMAGE_TYPES` constant.
**Warning signs:** "Template not found" errors on custom slides; custom-slide images generated but not shown in the UI.

### Pitfall 6: Cache-skip hides regenerated images
**What goes wrong:** `step-images` cache-skips when `inputHash` (over `{sizeRecord, imageType, promptsTmpl}`, `step-images.js:46`) is unchanged. If the prompt now comes from `slidesConfig` but the hash still uses the static `promptsTmpl`, editing a prompt won't invalidate the cache and regeneration silently no-ops.
**Why it happens:** The cache key doesn't include the editable prompt.
**How to avoid:** Include the slide's `generatedPrompt` (and attached file refs) in the `inputHash`, or always pass `force:true` from the UI (the existing item-regenerate already sends `force:true`, `PipelineApp.jsx:845`).
**Warning signs:** "Сгенерировать изображение" returns `{skipped:true}` after a prompt edit.

## Code Examples

### Seed defaults from `prompts.images.json` (D-03)
```javascript
// Source: pattern derived from config/prompts.images.json + IMAGE_TYPES (api/index.js:12)
const promptsTmpl = require(path.join(SHARED, 'config/prompts.images.json'));
const DEFAULT_LABELS = { main:'Главное фото', infographic:'Инфографика с размерами',
                         scale:'Масштаб с игрушкой', lifestyle:'Лайфстайл' };
function buildDefaultSlides() {
  return {
    feedbackSuffix: promptsTmpl.feedbackSuffix,                // D-06
    slides: promptsTmpl.imageTypes.map(id => ({
      id, label: DEFAULT_LABELS[id], default: true,
      description: (promptsTmpl.descriptions && promptsTmpl.descriptions[id]) || '', // add RU descriptions to the JSON
      generatedPrompt: promptsTmpl.prompts[id],               // existing EN prompt as starting value
      files: [],
    })),
  };
}
async function handleGetSlides(article) {
  const manifest = await store.getManifest(article);
  const cfg = manifest?.steps?.['03-images']?.slidesConfig;
  return respond(200, cfg || buildDefaultSlides());
}
```
> D-05 pre-fills default descriptions. `prompts.images.json` currently has only English `prompts`, no Russian `descriptions`. Adding a `descriptions` map to that file is still "defaults storage" (D-02 permits reading defaults from it — it forbids *writing generated prompts back*). Alternatively hardcode `DESCRIPTIONS` in the builder. Recommend adding a `descriptions` key to the JSON to keep it config-driven. `[VERIFIED: config/prompts.images.json — no descriptions key today]`

### Single-slide field update (read-modify-write, avoids Pitfall 1)
```javascript
async function patchSlide(article, slideId, patch) {
  const manifest = await store.getManifest(article);
  const cfg = manifest?.steps?.['03-images']?.slidesConfig || buildDefaultSlides();
  const slides = cfg.slides.map(s => s.id === slideId ? { ...s, ...patch } : s);
  await store.updateManifest(article, '03-images', { slidesConfig: { ...cfg, slides } });
  return slides.find(s => s.id === slideId);
}
```

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Path traversal via `slideId` or filename in `putArtifact` key | Tampering | Validate `slideId` regex; `path.basename` + char-whitelist on filename (existing pattern) |
| Prompt injection into the generate-prompt LLM call | Tampering/Info-disclosure | Low impact (output is a prompt the user reviews before use); keep system prompt fixed, treat description as untrusted user content — do not execute LLM output as code |
| Oversized/malicious file upload | DoS | busboy 15 MB/10-file limits + magic-byte gate already enforce this |
| MIME spoofing on attachments | Spoofing | `isImageBuffer` magic-byte check (`api/index.js:501`) — keep if images-only; if arbitrary types allowed (A5), add size caps + never serve with executable content-type |

**Note:** This is an internal single-team tool with no authentication by design (REQUIREMENTS.md "Out of Scope: OAuth / мультипользователи"). The security surface added by this phase is limited to input validation and file upload, both of which have existing, reusable mitigations in `api/index.js`.
